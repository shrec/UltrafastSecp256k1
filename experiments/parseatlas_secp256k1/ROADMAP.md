# ParseAtlas × secp256k1 — კვლევის როუდმეპი

განახლებულია: 2026-09-05. ეს არის ლოკალური სამუშაო გეგმა და არა შედეგის,
სისწრაფის, სრული ეკვივალენტობის ან სიახლის მტკიცებულება.

## მუშაობის რეჟიმი

მფლობელის მითითებით დროებით ვმუშაობთ Task MCP-ის გარეშე. შესრულება და
დამოუკიდებელი მენეჯერული მიმოხილვა გამიჯნულია; ჯერ მექანიკური შემოწმებები,
შემდეგ კოდი და მეთოდოლოგიური წესები. Task MCP-ის სტატუსები ამ ფაილით არ
იცვლება. სისტემის აღდგენისას საჭიროა არსებული ჩანაწერების შეთანხმება უკვე
გადმოტანილ ფაილებთან, არა იმავე ნამუშევრის ხელახლა გენერაცია ან გადაწერა.

ექსპერიმენტული ბრენჩია `experiment/representation-search`. გაყინული ძრავის
საწყისი რევიზიაა `fef231d4e4173bd016fb2a3a1eff67087396a203`.
Production კოდი, build-ის ნაგულისხმევი პარამეტრები და CI ამ ეტაპზე არ იცვლება.
არსებული `.gitignore` ცვლილება შენარჩუნებულია; ParseAtlas-ის კლონი იგნორირებულია.

მფლობელის ახალი მითითებით არითმეტიკული ექსპერიმენტები, მათი სისწორის gates,
დროის საზომი და პირველადი სტატისტიკა პირდაპირ C++-ში სრულდება. ისტორიული
Python-მოდელები ინახება როგორც წინა მათემატიკური არტეფაქტები; მიმდინარე
native კვლევის შესასრულებლად Python არ გაშვებულა.

## პირველი კვლევითი შეკითხვა: carry-ის ფასი region-ში

ჯერ შესასრულებელი ექსპერიმენტის კონტრაქტი, არა მიღებული შედეგი:

1. **ფიქსირებული ობიექტი:** word-დონეზე `a + b + carry_in`, შემდეგ იმავე
   სემანტიკის მრავალლიმბიანი შეკრება. დაბალი ბიტები და საბოლოო carry ორივე
   გამომავალია; შემდგომ modular ეტაპზე `p` და `n` ცალკე ობიექტებია.
2. **კონტროლი:** უცვლელი ძრავის შესაბამისი word/limb გზა, ზუსტად დაფიქსირებული
   backend-ით. თავდაპირველად reference მხოლოდ სისწორის კონტროლია; მისი მიმდინარე
   სისწრაფე ავტომატურად ვერ ამტკიცებს რომელიმე კანდიდატის უპირატესობას.
3. **წარმოდგენის პირველი განსხვავებები:** თანმიმდევრული carry; დამტკიცებული
   generate/propagate prefix; შეზღუდული redundant/carry-save state მთელი region-ის
   შიგნით. ეს ცნობილი მეთოდების გასამეორებელი კონტროლებია, არა სიახლის განაცხადი.
   შერჩევა წარმოადგენს 25-პოლიტიკიანი ატლასის პირველ ჭრილს და არა მის ჩანაცვლებას.
4. **საზღვარი:** encode, state update, decode და ნორმალიზაცია აშკარადაა აღწერილი.
   შევადარებთ ერთ ოპერაციასაც და ერთჯერადი encode/decode-ით მთელ განმეორებად
   region-საც. მხოლოდ შიდა ოპერაციის იაფი ფასი საბოლოო სარგებელს არ ნიშნავს.
5. **ორაკულები და უარყოფითი კონტროლები:** 0, მაქსიმალური word, სრული/გაწყვეტილი
   carry-ჯაჭვი, carry-in 0/1, მოდულთან ახლო მნიშვნელობები, დაშვებული aliasing;
   მიზანმიმართულად დაკარგული carry, დარღვეული limb bound და მცდარი decode უნდა
   ჩავარდეს. არასწორ input-ს ცალკე აქვს განსაზღვრული კონტრაქტი.
6. **დაკვირვებები:** კრიტიკული გზის სიღრმე, პიკური ცოცხალი მნიშვნელობები,
   ოპერაციების მულტისიმრავლე, encode/decode-ის ოპერაციები და დრო, region-ის
   latency/throughput. Static depth/live-set არ არის CPU-ს დრო ან რეალური
   register allocation; compiler/disassembly და გაზომვა ცალკე მტკიცებულებებია.
7. **შერჩევის რიგი:** მიღწევადობა → დამტკიცებული boundary equivalence →
   invariants/CT eligibility → რესურსის ბიუჯეტში ჩატევა → მხოლოდ ამის შემდეგ
   ცალკეული ფასების Pareto შედარება. კორპუსზე დამთხვევა რჩება `OBSERVED`;
   მხოლოდ ამით კანდიდატი production-ისთვის მისაღები არ ხდება.
8. **გამძლეობის შემოწმება:** ერთი და იმავე DAG-ის განსხვავებული ჩაწერა არის
   null control; აზრიანი ცვლილება უნდა ცვლიდეს წარმოდგენას ან კანონიერ DAG-ს.
   ფიქსირდება tie-break-ის ოპტიმისტური/პესიმისტური ვარიანტები, უცვლელი და მოძრავი
   შემთხვევები ცალ-ცალკე, და წესების გაყინვის შემდეგ — held-out ობიექტები.

ნამდვილი არსებული საზღვრის მაგალითია `FieldElement52::from_fe` (ბიტების
გადანაწილება) და `FieldElement52::to_fe` (ნორმალიზაცია და უკან შეფუთვა),
`field_52_impl.hpp:2744–2769`. `FieldElement::to_bytes` თვითონ არ აკეთებს
ნორმალიზაციას. ეს აღწერს წყაროს და არ არის ახალი ექსპერიმენტის შედეგი.

## პირველი გამეორებადი L0 დაკვირვება

[რეფერენსის დიაგნოსტიკაში](L0_REFERENCE_CHECK.md) შენახულია ორაკულთან
კონკრეტული უთანხმოება: ორ მაქსიმალურ 64-ბიტიან სიტყვაზე `mulhi64`-ის
სპეციალურად არჩეული schoolbook fallback აბრუნებს ზედა სიტყვას
`fffffffefffffffe`, ხოლო bigint-ით სწორი მნიშვნელობაა `fffffffffffffffe`.
შუალედურ ჯამს 65 ბიტი სჭირდება; დაკარგული carry ზედა სიტყვაში `2^32`-ს აკლებს.
სამივე probe-build და დამოუკიდებელი bigint შედარება გამეორებულია.

ეს არის `OBSERVED` კონტრმაგალითი გაყინული წყაროს კონკრეტულ განშტოებაზე,
არა 25-სამყაროს ექსპერიმენტი ან ახალი მათემატიკური მეთოდი. ჩვეულებრივი
`__int128` კონტროლი ამ შეყვანაზე ემთხვევა ორაკულს; production-ში fallback-ის
გამოყენება ამ დიაგნოსტიკით არ დადგენილა. Production-ის ცვლილება არ გაკეთებულა.

რეფერენსი და bigint თუ განსხვავდება, ჩანაწერი ვერ მიიღებს სისწორის გავლის
ნიშანს მხოლოდ ბაიტური დამთხვევის გამო. უთანხმოება ინახება უცვლელად; არ
ვასწორებთ decode-ს მის დასამალად და ავტომატურად არ ვცვლით გაყინულ baseline-ს.
ანგარიშის მკაცრი შედარება განზრახ აბრუნებს exit 1-ს. ეს განცალკევებულია
მეთოდოლოგიის/ინვენტარის წარმატებული ტესტებისგან.

## L0 წარმოდგენის ბირთვი — პირველი დასრულებული ჭრილი

[შესრულებადი მოდელი და ანგარიში](REGION_MODEL.md) მოიცავს 1–64-ბიტიან
სიტყვებს, 1–4 limb-ს, აშკარა carry-ს, ტიპიზებულ DAG-ს და ზუსტად რეგისტრირებული
serial→prefix წარმოების ხელახლა შესრულებას. თვითნებური კანონიერი DAG ავტომატურად
ეკვივალენტური არ არის; არც serial მოდელია გაყინული C++ ენჯინის შესრულება.

საბოლოო ბირთვზე შემოწმებულია ყველა 131,072 რვაბიტიანი `(a,b,carry_in)`
შეყვანა ორ განლაგებაში — `(word_bits,limbs)=(4,2)` და `(2,4)` — ორივე
ალგორითმით: სულ 524,288 შესრულება, bigint-თან უთანხმოების გარეშე.
ეს არის მცირე განსაზღვრული დომენის `OBSERVED` შედეგი, არა 256-ბიტიანი მტკიცებულება.

4×64-bit სტატიკურ მოდელში serial-ს აქვს 4 ოპერაცია/სიღრმე 4, prefix-ს —
14 ოპერაცია/სიღრმე 5. ამ ოპერაციულ მოდელში უპირატესობა არ ჩანს; ეს არ არის
CPU-ს გაზომვა ან production-ის რეიტინგი. მიმოხილვისას ნაპოვნი `FINISH`-ის
დაუშვებელი carry=2 ახლა უარყოფილია და რეგრესიის ტესტითაა დაცული.

შემდგომ baseline-ეტაპზე დეტერმინისტული word/limb კორპუსი გაყინულია და
უცვლელი C++ reference დაკავშირებულია დაბალ ბაიტებსა და carry-სთან.
შემდეგი ნაბიჯია 25-ლინზიანი სინთეზიდან მიღებული ჰიპოთეზების კონტრაქტის
გაყინვა და მხოლოდ ამის შემდეგ იმავე boundary-ზე კანდიდატისა და ხელახლა
გაშვებული კონტროლის შედარება; შემდეგ — bounded redundant/carry-save region და ცალ-ცალკე Fp/Fn
მოდულური საზღვრები. 25-სამყაროს ზოგადი ძიება და მუდმივი დროის დასტური
ჯერ არ განხორციელებულა; hardware-ზე ამ ეტაპზე მხოლოდ L0 baseline-ებია გაზომილი.

## L0 baseline — შესრულებული საწყისი გაზომვა

[გაზომვების ანგარიში](L0_BASELINES.md) და [პროტოკოლი](BASELINE_PROTOCOL.md)
აფიქსირებს უცვლელი `add64`-ის ერთსიტყვიან და ოთხლიმბიან harness-კომპოზიციას:
დამოკიდებული ჯაჭვი, ცხელი მასივი და დიდი მასივი — ექვსი რეჟიმი.
ეს არ არის production Fp/Fn შეკრება ან ახალი მეთოდის აჩქარება.

ორ ცალკე CPU-ს სერიაში შენახულია 84 დროითი ნიმუში; არცერთი ამოგვიგდია.
CPU 0-ის სერია არასტაბილურია, რის შემდეგაც შეგროვდა CPU 4-ის დამატებითი
სერია; ისინი არ გაერთიანებულა. CPU 4-ზე ოთხლიმბიანი ცხელი რეჟიმის მედიანაა
3.005 ns, დიდის — 6.536 ns. იგივე არითმეტიკის განსხვავებული სამუშაო ნაკრები
სხვადასხვა დროს იძლევა; უშუალოდ DRAM bottleneck ან „მეტი ოპერაციის მოგება“
ამით ჯერ არ დასტურდება. მთელი პროცესის perf counters ცალკე არტეფაქტია,
არა მხოლოდ შიდა kernel-ის დათვლა. სისტემური პარამეტრები უცვლელია.

კორპუსზე 610+1024 შემთხვევაში გამომავალი ბაიტები და carry bigint-ს ემთხვევა;
ოთხი პატარა benchmark kernel შემოწმებულია replay-ით, დიდი დროითი გაშვებების
ყველა output — არა. Actual binary disassembly ადასტურებს ოთხლიმბიანი
დამოკიდებული ჯაჭვის stack spill-ებს; static live-set register allocation არაა.

შემდეგი შედარება მოითხოვს ახალ, იმავე სესიაში მონაცვლეობით გაშვებულ
ორიგინალ კონტროლსა და კანდიდატს, ერთნაირი input/output boundary-ით.
Encode/decode, normalization, locality და სრული region-ის ხარჯი უნდა შევიდეს.
ამ ისტორიულ baseline snapshot-ში prefix/carry-save კანდიდატი ჯერ არ გაზომილა.
შემდგომი native კონტროლები ქვემოთაა; carry-save, held-out კორპუსი და CT gates დარჩენილია.

## ფენა-ფენა გაფართოება

წარმოდგენა, რომელსაც ზედა caller-ისთვის განსაზღვრული საზღვარი და საჭირო
სისწორის/დიაპაზონის მტკიცებულება აქვს. უარყოფითი შედეგი შემოიფარგლება ზუსტად
