## შედეგი

დამოკიდებულ, rotate/XOR-ით განახლებად ჯაჭვში `gp_recomputed`-ის წყვილური
Original/candidate შეფარდების მედიანა ორ სერიაში იყო **1.497× / 1.534×**.
დამოუკიდებელ შეკრებებში, როგორც პატარა, ისე დიდ მასივზე, **Original-ს ორივე
სერიაში ყველაზე დაბალი მედიანა აქვს**. ერთი და იგივე მეთოდი ერთ კონტექსტში
იგებს, მეორეში აგებს; ეს არ არის ზოგადად უფრო სწრაფი adder ან მთელი
secp256k1 ენჯინის აჩქარება.

ყველა ახალი არითმეტიკული ტესტი, benchmark, დროის საზომი და პირველადი
სტატისტიკა შესრულდა **C++-ში**. Python ამ ექსპერიმენტში არ გაშვებულა.
მენეჯერმა უკვე გამოტანილი JSON-ის რიცხვები ცალკე JavaScript-ით გადაამოწმა;
ეს არც არითმეტიკის რეალიზაციაა და არც დროით ინტერვალში შედის.
ისტორიული Python-მოდელები უცვლელად რჩება, როგორც მათემატიკური კვლევის არტეფაქტები.

## რას ვადარებთ

სრული საზღვარია `a+b+carry_in = low + carry_out*2^256`: ოთხი 64-ბიტიანი
limb, ყველა 32 დაბალი გამომავალი ბაიტი და საბოლოო carry ბიტი. შემომავალი
carry მხოლოდ 0 ან 1-ია. ეს ჯერ **არ არის mod-p/mod-n ოპერაცია**.

Original ოთხჯერ იყენებს ძრავის უცვლელ `detail::add64`-ს.
დანარჩენი სამი ცნობილი კონტროლია: GP შუალედურების წყაროში შენახვა,
წყაროში ხელახალი გამოთვლა და carry-ის დალაგებული 2+2 ბლოკი.
ყველა იყენებს ერთსა და იმავე input/output განლაგებას; ზოგადი overlapping-buffer
API არ გამოცდილია. ახალი კანდიდატების თავისუფალი გენერატორი ან V11 extractor
არ დამატებულა: ეს ხელით განსაზღვრული H01/H02 კონტროლების პირველი native ჭრილია.

[წინასწარი პროტოკოლი](NATIVE_COMPARE_PROTOCOL.md) და
[ორ-სერიანი გეგმა](data/l0_native_run_plan_20260905.json) დაფიქსირდა გაზომვამდე.
ერთი და იგივე ბინარი, GCC 14.2, `-O3 -march=native -DNDEBUG -Wall -Wextra`,
C++17, CPU4, i5-14400F. CPU4-ის L1d=48 KiB, LLC=20 MiB.
დაფიქსირებული governor არის performance; turbo გამორთული იყო;
სიხშირის ცალკეული საწყისი/საბოლოო წაკითხვა — 2.5 GHz.
ეს უწყვეტი სიხშირის კონტროლი არ არის. ჩვენ სისტემის პარამეტრები არ შეგვიცვლია.

| მეთოდი | დამოკიდებული ჯაჭვი, ns/add | ცხელი მასივი, ns/add | დიდი მასივი, ns/add |
|---|---:|---:|---:|
| `original` | 12.292 / 12.434 | 2.887 / 3.118 | 7.333 / 6.949 |
| `gp_materialized` | 13.566 / 13.644 | 6.581 / 8.631 | 8.797 / 8.397 |
| `gp_recomputed` | 8.292 / 8.073 | 6.922 / 7.169 | 9.726 / 8.447 |
| `blocked2` | 12.630 / 12.623 | 4.774 / 5.056 | 8.432 / 7.517 |

თითო უჯრედშია **სერია 1 / სერია 2-ის მედიანა**, არა საუკეთესო ნიმუში.
დამოკიდებული ჯაჭვის დროში შედის `b[j]=rotl(b[j],13) XOR new_a[j]`,
ციკლები და კომპილატორის რეალური spills; ეს იზოლირებული ADD/ADC latency არაა.
ცხელი მასივია 219 ჩანაწერი / 24,528 ლოგიკური ბაიტი; დიდი —
748,983 ჩანაწერი / 83,886,096 ლოგიკური ბაიტი. Bulk ორივეგან იყენებს
იგივე 72-ბაიტიან input-სა და 40-ბაიტიან output-ს.

თითო რეჟიმში: ორი warmup წრე, შვიდი გაზომილი წრე და ოთხივე მეთოდის
წინასწარ დათესილი, მბრუნავი რიგი. ჯამში **168 გაზომილი ნიმუში**.
სერიები არ გაერთიანებულა და საუკეთესო შედეგი არ შერჩეულა.
წყვილური შეფარდება თითო წრის Original/method დროებიდან ითვლება;
მისი მედიანა ცალკეული დროების მედიანების შეფარდება აუცილებლობით არ არის.

Original-ით კალიბრაცია 200 ms-ს მიაღწია, მაგრამ ფიქსირებული საერთო სამუშაოს
შემდგომი 21 ნიმუში 200 ms-ზე მოკლე აღმოჩნდა; ყველა შენარჩუნებულია.
მინიმუმი სერია 1-ში 128.416 ms, სერია 2-ში 144.954 ms იყო.
მეთოდები შვიდ წრეში პოზიციებზე იდეალურად დაბალანსებული არ არის;
რეჟიმების რიგი ფიქსირებულია: latency → hot → large.

შეზღუდვების მნიშვნელოვანი მაგალითები:

- `gp_recomputed` latency-ის 14 წყვილიდან 13-ში სწრაფია. სერია 2-ის ერთი
  12.910 ns ნიმუში იმავე წრის Original-ზე ნელია (შეფარდება 0.959); არ ამოგვიღია.
- ამავე მეთოდის hot წყვილური მედიანებია 0.416 / 0.416, large — 0.741 / 0.818.
  ჯაჭვის მოგება bulk-ის მოგებად ვერ გადაიქცევა.
- სერია 2-ის hot Original მერყეობს 2.866–4.749 ns-ში; გარე დატვირთვა,
  sibling-core აქტივობა და თერმული მდგომარეობა იზოლირებული არ ყოფილა.
  შეფარდებები აღწერითი სტატისტიკაა, არა confidence interval ან მიზეზის მტკიცება.
- ისტორიულ სხვა harness-ში მიღებული Original ≈4.90 ns არ არის ამ კანდიდატების
  denominator. ახალი ჯაჭვის ≈12.3 ns-თან სხვაობის მიზეზი ჯერ გამოსაყოფია.

## სისწორის მექანიკური gates

[Native ტესტი](tests/test_l0_native.cpp) სრულ შედეგს ადარებს
`boost::multiprecision::cpp_int`-ს და უცვლელ Original-ს.
ყველა build-ზე დაფიქსირდა:

- 100,000 seeded random + 43,762 boundary = **143,762 სრული ზომის შემთხვევა**;
- ოთხ მეთოდზე **575,048 სრული ბაიტების/carry-ის შედარება**, **0 უთანხმოება**;
- დამატებით 10 პატარა განლაგება, 18,248 input triple განლაგებების ჯამში,
  **55,528 სრული output შემოწმება**;
- 16 GP-კომპოზიცია, 27 ასოციაციური სამეული; lossy state-ის 20
  არაასოციაციური სამეული და high=2-ის საჭიროების ოთხი შემთხვევა შენარჩუნებულია.

ეს ერთი დეტერმინისტული კორპუსია: boundary-ებში დუბლიკატებია; სხვადასხვა build
უნიკალური კორპუსის ზომას არ ამრავლებს. გადის GCC native, GCC
`SECP256K1_NO_INT128`, Clang 18.1.3 native და GCC UBSan.
`-DNDEBUG` აუცილებელ checks-ს არ თიშავს. Native driver-ის ჩვეულებრივი და
UBSan smoke გადის; მენეჯერის ექვსი არასწორი CLI კონტროლი exit 2-ს აბრუნებს.
მშენებლის დამატებითი CLI შემოწმებები დამოუკიდებელ მენეჯერულ რაოდენობაში არ აგვირევია.

Benchmark-ის ყველა bulk input წინასწარ მოწმდება Original-თან.
Latency-ზე პირველი 4096 ნაბიჯი სრულად შედარდება, შემდეგ მთელი ჯაჭვის საბოლოო
digest — untimed Original replay-ს. ეს ბოლო digest შედარება ყველა შიდა
მდგომარეობის შემოწმების ტოლფასი არ არის. დამოუკიდებელი bigint ორაკული ცალკე
ტესტშია და არა benchmark-ის დროით მონაკვეთში.
არცერთი finite gate არ აცხადებს სრულ 256-ბიტიან ან constant-time მტკიცებულებას.

## რას აჩვენებს რეალური ასემბლერი

გაზომილი და დამოუკიდებლად განხილული ბინარის SHA-256:
`db861f408d60f9768dec947c3164834e17280c0ab73fc27e853ec8622378b764`.
[შენახულ ასემბლერში](data/l0_native_disassembly_20260905.txt) რვავე timed wrapper-ს
აქვს შენარჩუნებული გამოთვლის ციკლი; თითო შეკრებაზე dispatch/oracle/checksum
გამოძახება არ არის. სრული output ან recurrence state ცოცხალია.

| bulk მეთოდი | ძირითადი ციკლის მისამართები | instruction ჩანაწერები | `rsp`-ით მისამართებული ჩანაწერები |
|---|---|---:|---:|
| Original | 0x9730–0x97be | 39 | 0 |
| GP materialized | 0x8940–0x8a73 | 89 | 5 |
| GP recomputed | 0x8e80–0x8fc8 | 92 | 7 |
| Blocked2 | 0x9330–0x9419 | 65 | 0 |

ეს სტატიკური disassembly-ჩანაწერებია, არა retired instructions, µops,
cycles ან მეხსიერების ბაიტები. არც wrapper-ის სრული ზომაა სუფთა kernel-ის ზომა.
ორივე GP ვერსია განსხვავებულ instruction schedule-ად დაკომპილირდა;
წყაროში გამეორებული გამოთვლების ნაწილი compiler CSE-მ გააერთიანა.
ამიტომ `gp_recomputed` სახელიდან „მეტი შესრულებული ALU და ნაკლები load“
ვერ დავასკვნით. ოთხივე latency ვერსიაში stack traffic ჩანს.

ამ ეტაპის დასკვნაა **კონტექსტისა და code generation-ის მიმართ მგრძნობელობა**.
სწორედ spills-ის, scheduling-ის ან dependency-path-ის ცალკეული მიზეზობრივი
წილი ჯერ გაზომილი არ არის. PMU არ შეგვიგროვებია; ძველი whole-process counters
ახალ ბინარს არ მიეწერება. 112 ლოგიკური byte/add DRAM bandwidth არ არის.
