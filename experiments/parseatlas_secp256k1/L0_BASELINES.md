# L0 baseline — გაზომილი საწყისი მდგომარეობა

თარიღი: 2026-09-05. ბრენჩი: `experiment/representation-search`.
დროები და მრიცხველები: `MEASURED`; სასრული კორპუსის სისწორე: `OBSERVED`.
ორივე შემოიფარგლება მითითებული პირობებით; არცერთი არ ნიშნავს `PROVEN`-ს.
ახალი მეთოდის აჩქარება ან სიახლე ამ ეტაპზე არ გამოცხადებულა.

## რა მივიღეთ

არსებული `secp256k1::detail::add64`-ის ექვსი სამუშაო რეჟიმი გავზომეთ:
1×64 და 4×64 ბიტი, თითოეული დამოკიდებული ჯაჭვით, მცირე ცხელი მასივით
და დიდ მასივზე მიმდევრობითი გავლით. თითო სერიაში არის 7 გამეორება და
2 წინასწარი გახურება თითო რეჟიმზე. ორი CPU-ს სერიაში სულ **84 დროითი ნიმუშია**;
ყველა გაზომილი შიდა ინტერვალი მინიმუმ 200 ms იყო.

4×64 ბიტი ნიშნავს ოთხი უცვლელი `add64` გამოძახების carry-ჯაჭვს სატესტო
პროგრამაში. ეს **არ არის** production `FieldElement`/`Scalar`-ის მოდულური
შეკრება, მთელი secp256k1 ენჯინის გაზომვა ან prefix/carry-save კანდიდატი.
`p`-ზე/`n`-ზე reduction ჯერ არ შედის.

კვლევის სრული ტესტები: **366 passed** — წინა 199, C++ harness-ის 76 და runner-ის 91.
სისწორის ცალკე გაყინული კორპუსია **610 ერთსიტყვიანი + 1024 ოთხლიმბიანი შემთხვევა**:
დაბალი გამომავალი ბაიტები და carry დამოუკიდებელ bigint-ს ემთხვევა.
ეს არის სასრული კორპუსის შემოწმება და არა ყველა 256-ბიტიანი შეყვანის მტკიცებულება.
ოთხივე პატარა benchmark kernel-იც bigint replay-ითაა შემოწმებული;
დიდი დროითი გაშვებების ყველა გამომავალი bigint-ით არ გადამოწმებულა —
მათთვის შენახულია გამეორებებს შორის სტაბილური checksum.

## დროები

ქვემოთ არის CPU 4-ზე დამატებითი სერია. ერთეული: **ns / სრული ლოგიკური შეკრება**;
ოთხლიმბიანი შედეგი ოთხ limb-სა და საბოლოო carry-ს მოიცავს, არა ერთ limb-ს.
ფრჩხილებში შვიდივე ნიმუშის მინიმუმი–მაქსიმუმია; არცერთი ნიმუში არ ამოგვიგდია.

| რეჟიმი | 1×64 ბიტი, მედიანა (დიაპაზონი) | 4×64 ბიტი, მედიანა (დიაპაზონი) |
|---|---:|---:|
| დამოკიდებული ჯაჭვი | 1.217 (1.209–1.234) | 4.900 (4.874–5.057) |
| მცირე, ცხელი მასივი | 1.231 (1.228–1.280) | 3.005 (2.971–3.077) |
| დიდი მასივი, მიმდევრობითი გავლა | 2.335 (2.280–2.476) | 6.536 (6.324–7.965) |

ეს საწყისი მდგომარეობის გაზომვებია და არა მომავალი კანდიდატისთვის მუდმივი
სამიზნე რიცხვები. თავდაპირველ CPU 0 სერიაში პირველი ორი წრის შემდეგ რამდენიმე
რეჟიმი ერთდროულად შენელდა. CPU 4 **ამ არასტაბილურობის ნახვის შემდეგ** ავირჩიეთ
დამატებითი დაკვირვებისთვის. სერიებს არ ვაერთიანებთ და განსხვავებას core-ის
უპირატესობად არ ვაცხადებთ. კონკრეტული მიზეზი არ დაგვიდგენია.

CPU 0-ის მედიანები იგივე რიგით: ერთსიტყვიანი **1.956 / 2.370 / 2.863 ns**;
ოთხლიმბიანი **6.399 / 5.962 / 8.012 ns**. მაგალითად, მისი ოთხლიმბიანი ცხელი
სერიის ყველა ნიმუშია: 3.040, 3.141, 6.350, 6.353, 6.266, 5.962, 4.572 ns.
ეს სერია შენარჩუნებულია როგორც გარემოს არასტაბილურობის მტკიცებულება.
CPU 4-ის დიდ ოთხლიმბიან რეჟიმშიც 7.965 ns ნიმუში დარჩენილია.
Median/MAD/IQR აღწერითი სტატისტიკაა და არა ნდობის ინტერვალი ან
ავტომატური ზღვარი მცირე აჩქარების მისაღებად.

## რას ამბობს ეს ლოკალურობაზე

ოთხლიმბიან შემთხვევაში იგივე შეკრების კოდი ცხელი მასივით დაახლოებით
**3.01 ns**, დიდი მასივით კი **6.54 ns** გამოვიდა. ოპერაციების ფორმალური
რაოდენობა მარტო შესრულების დროს ვერ აღწერს; მონაცემების განლაგება და სამუშაო
ნაკრების ზომა აუცილებელი ცალკე დაკვირვებებია. ეს შეესაბამება კვლევის კითხვას:
შეიძლება მეტი არითმეტიკა ნაკლებ გადაადგილებასა და უკეთეს ლოკალურობას ცვლიდეს.

მაგრამ ამ გაშვებით **ჯერ არ შეგვიდარებია მეტი და ნაკლები ოპერაციის მეთოდები**,
არც შენელების მიზეზი გამოგვიყვია კონტროლირებული ექსპერიმენტით.
დადასტურებულია დროის განსხვავება ამ ორ რეჟიმში, არა ახალი ალგორითმის მოგება
ან უშუალოდ DRAM bandwidth-ის შეზღუდვა.

მასივის ლოგიკური ჩანაწერი input+output-ით არის 40 B ერთსიტყვიან და
112 B ოთხლიმბიან რეჟიმში. ცხელი ნაკრებებია 24,560 / 24,528 B;
დიდი ნაკრებები — 83,886,080 / 83,886,096 B.
მანქანაზე P-core-ის L1d არის 48 KiB, L2 — 1280 KiB, საერთო L3 — 20 MiB.
`logical_GBps` მიღებულია ჩანაწერის ზომიდან: დიდ რეჟიმებში დაახლოებით
17.13 / 17.14 GB/s. ეს **არ არის გაზომილი DRAM ტრაფიკი**;
compiler-მა carry-ის რვაბაიტიანი სლოტიდან შეიძლება მხოლოდ ერთი ბაიტი წაიკითხოს,
ხოლო cache/write-allocation სხვა ტრაფიკსაც ქმნიდეს.

დამოკიდებული ჯაჭვი შეიცავს `rotate/XOR`-ით მომდევნო input-ის მომზადებას,
ციკლსა და შესაძლო spill-ებს. ის **არ ზომავს იზოლირებული ADC-ის latency-ს**.
გაზომილი ბინარის disassembly-ში ოთხლიმბიან ჯაჭვს stack-ზე load/store აქვს:
მოდელის მცირე live-set რეალურ register residency-ს არ ამტკიცებს.
მისი `logical_bytes_per_op=0` მხოლოდ bulk მასივის ნაკადის არქონაა.

ოთხლიმბიანი ცხელი/დიდი რეჟიმები დამატებით გავუშვით `perf stat -r 3`-ით.

ეს მრიცხველები მოიცავს **მთელ user-space პროცესს** — ინიციალიზაციას,
გახურებასა და checksum-საც — და არა მხოლოდ შიდა გაზომილ შეკრებებს.
შენახულია perf-ის გაერთიანებული მნიშვნელობები და ვარიაცია;
თითო გამეორების ცალკე PMU რაოდენობები არ გვაქვს.

Generic cache event-ები არ არის memory-controller/DRAM bytes.
ეს სამი გამეორება შვიდნიმუშიან მთავარ სერიებში არ შეგვირევია.

## შემდეგი შედარების კონტრაქტი

1. ორიგინალი კონტროლი და კანდიდატი **იმავე ახალ სესიაში**, მონაცვლეობით,
   თანაბარი input-ით/გამომავალი ბაიტებითა და ერთი boundary-ით უნდა გაიზომოს.
   დღევანდელ საუკეთესო დროსთან შედარება საკმარისი არ არის.
2. პირველად ცალ-ცალკე იცვლება carry-მეთოდი ან განლაგება/working-set.
   ცნობილ serial/prefix კონტროლებს შემდეგ ემატება bounded carry-save region.
   ხარჯში შედის encode/decode, normalization და სრული output-ის materialization.
3. ერთად იწერება ოპერაციები, critical path, რეალური compiler spills,
   დრო და მკაფიო საზღვრის მქონე memory counters. ზედმეტი ოპერაცია
   ავტომატურად არ ნიშნავს წაგებას; მცირე static depth — მოგებას.
